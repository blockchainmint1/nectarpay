# src/lib rules
- Fast website prefill uses the linked Firecrawl gateway, public HTTPS DNS names only, and at most homepage plus same-origin contact page; suggestions fill blank fields and never establish ownership or consent. Why: reduce typing without trusting website content or making local arbitrary-URL requests.
- Cold Storage Coin sticker invoices use a static TXC address, TSD only, one active checkout per address, a pre-checkout transaction snapshot, exact full-sale matching (including verified Give splits), and atomic sticker txid claims before recording or settlement. Why: a shared address must not miscredit concurrent or historical payments.
- eGiving community splits: only Omni send-to-many TSD credits to stores with egiving_enabled qualify, and every non-merchant output must be an active egiving_recipients address (exactly one program, at least one church, shares summing to the invoice); the merchant slice must reach (100 - EGIVING_DISCOUNT_PCT)% with no tolerance, and the invoice is tagged payment_program/discount_usd before settling. Why: a split must never let ordinary underpayments through.
- The eGiving discount comes from EGIVING_DISCOUNT_PCT in src/lib/egiving.ts, never from stores.egiving_discount_pct; that column is read-only to authenticated (column-level UPDATE/INSERT revoked) and shown disabled in the merchant UI. Why: the eGiving wallet hard-codes its 8% church / 2% program split, so a per-store value would make its fixed payment arrive underpaid.
- The public eGiving cause list (/api/public/v1/egiving/causes) comes only from get_public_egiving_causes() (active churches, never the program) and every response is TXC-message-signed with a key derived from EGIVING_LIST_SIGNING_KEY. Why: wallets pin the signer address so a compromised server cannot swap a church address.
- eGiving churches and participating merchants are managed only in Admin → Give; the HME Give signed-list feed (src/lib/hme-give-registry*) is switched off via HME_GIVE_SYNC_ENABLED, so the cron and /api/public/hooks/hme-give change nothing. Why: Bobby chose NectarPay as the single place to manage Give.
- Fast Start merchant signatures are image files in the private fast-start-signatures bucket (fast_enrollments.signature_path); the browser never lists or reads that bucket, and src/lib/fast-consent.server.ts hands the image back only through an admin-checked server function. Why: the drawing is evidence of the merchant's agreement and must stay readable later without becoming publicly fetchable.
- Single-address EVM mode (stores.evm_address_rotation = false, the default for new stores) pays every EVM sale to index 0 with a unique sub-cent amount tail; every EVM watcher path must resolve transfers to index-0 invoices through resolveSharedEvmTransfer/pickSharedInvoice (exact tail, else the lone sale within a cent) and park anything else in unmatched_payments for the merchant. Why: one shared address must never credit one payment to several sales or guess between them.
- Stores without an activated Cold Storage Coin get slug stickers at /s/<url_slug> (src/lib/store-sticker.server.ts): each scan opens a chain-less invoice so /i/<id> derives a fresh address from the store wallet; coin-backed stores resolve to their coin sticker. Why: static-address guards apply only to coin stickers.
- Shopper redirect links (invoices.redirect_url, KYC hand-offs) must pass safeHttpUrl (src/lib/safe-url.ts) at input and again before navigation; a database check constraint also enforces http(s). Why: javascript:/data: links run code on the checkout origin and can steal merchant sessions.
- Security alerts (wallet-key changes) call notifyUser with force: true, which ignores mute switches, emails the sign-in address and copies platform admins. Why: a hijacked session could otherwise silence the alert before swapping keys.
- Signed-in (authenticated/anon) writes to invoices pass the guard_invoice_user_writes trigger: inserts must be pending with no payment details, and updates may only touch email/expiry fields or cancel an unpaid sale; status and payment fields are written by server code with the service role. Why: merchants could otherwise mark their own sales paid, which triggers paid-page redirects, receipts and webhooks without any payment.
- Lightning is off platform-wide: src/lib/lightning-switch.ts gates the merchant settings card, invoice creation and the Lightning cron, and the chain_configs_lightning_disabled check constraint refuses enabled Lightning rows; re-enabling needs both changed. Why: nobody used it, and a dormant custodial payout path is pure risk.
- Payout destinations outside chain_configs (stores.usdc_payout_address_eth for Tangem) are written only through server functions behind authorizeKeyChange plus the emailed code; the store_payout_cooloff trigger holds new values 4 hours, logs a security_events row, and promote_due_chain_keys activates them. Why: every way of redirecting money must share the same hold and unmutable alert.
- chain_key_cooloff holds any first key on a coin once the store is established (another coin keyed for 15+ minutes), except when it reuses a wallet the store already pays into. Why: adding a never-used coin otherwise redirects new sales instantly.
- Wallet/payout change codes go to the store owner's sign-in email when a non-owner, non-platform-admin acts (src/lib/key-change-code.ts); the same code is required for such a member to cancel a pending change. Team management server functions check mfa_ok() themselves because they write with the service role. Why: a planted full-access member must not approve or block payout changes from its own mailbox.
- Open sales on shared addresses (EVM/Solana/Tron) are unique per (address, token, amount) via invoices_open_shared_amount_unique; writers retry derivation on that collision (src/lib/open-amount-collision.ts). Why: two simultaneous sales must never ask for the same amount.
- Public tools that spend third-party credits count calls with bump_public_rate (hashed visitor address) before working. Why: unauthenticated scraping is a cost vector.
- The Solana and Tron watcher paths scan only wallets with an open sale on that chain and stop at history older than the oldest open sale minus the pre-invoice grace (src/lib/watcher-scan-plan.ts). Why: the 10-second watcher otherwise re-reads every merchant wallet's history, which burned ~250k paid RPC calls a day with no sales open.
- Tron, Solana, Bitcoin Cash, Dash and BNB Chain (bsc) are retired: src/lib/network-switch.ts hides them from store settings and refuses new invoices, and the chain_configs_force_retired_off trigger keeps them disabled while preserving saved keys; bsc is also dropped from EVM_NETWORKS, EVM_CHAIN_KEYS and the Alchemy push sync because it shares the eth wallet row, but src/lib/bsc-mistake-watch.server.ts still watches BNB Chain stablecoin transfers to addresses with an open stablecoin sale (free public node, capped catch-up) through the normal EVM matching, relabelling a credited sale as bsc. Why: their watchers cost paid RPC calls, yet shoppers still send USDT on BNB Chain to the shared 0x address by mistake.
- Callback (webhook) alerts fire on any link change, or a secret change while a link exists; server-side secret rotation goes through rotate_store_webhook_secret so log_security_event can read the caller from nectar.actor_id. Why: setup used to send an extra alert signed 'an unknown' for a secret that could not redirect anything.
- Store webhooks are an outbox: the invoices_enqueue_webhooks trigger saves webhook_deliveries rows in the same step that settles a sale, and src/lib/webhook-outbox.server.ts sends, logs and retries them (settlement sends first, the watcher picks up anything due). Never POST a store webhook outside it. Why: a request cut off after settlement lost callbacks with no record or retry.
- Wallet balances count every sale address from the first sale index (#0 only for single-address EVM stores) to the highest of the address counter and any sale's address_index, paged through getChainBalances (src/lib/balance-pages.ts) and loaded by the shared useWalletScan hook (at most three pages in flight app-wide; the store card and Wallet balances page share its cache); per-coin and per-network totals come from summarizeWalletScan (src/lib/wallet-assets.ts). EVM reads every known stablecoin on the network, not only checkout-enabled ones; TSD and other Omni tokens are rebuilt from full address history (omniBalanceFromTxs); pasted single addresses are read as static; retired networks show only when they hold money. Why: a 20-address cap and native-only reads hid most TXC sales and all TSD, and money that arrives is in the wallet whatever checkout allowed.
