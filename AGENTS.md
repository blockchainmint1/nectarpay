- ZCU (chain id 90031273) is an EVM chain sharing the ETH xpub but scanned via its own RPC (src/lib/chains/zcu.server.ts), not Alchemy; native only; price comes from wzcu.zerochill.com Uniswap 30m TWAP in pollRates (admin override available).
- EVM push notifications are hints: resolve assets by configured contracts and use the shared on-chain scanner and guarded transaction recorder before settlement, so token metadata cannot authorize payment.
- Direct user grants on stores, terminals, and API keys must exclude secret reads; secret writes use authorized server operations (API-key fingerprint insertion is write-only), so team row visibility cannot reveal credentials.
- Every new editable store-profile column must ship with column-level authenticated SELECT/UPDATE/INSERT grants, keeping existing RLS intact; table-wide grants would expose store secrets.
- Wallet login verifies the persisted server-issued message, uses allowlisted callback origins, and binds token polling/exchange to an HttpOnly browser cookie; conditional state transitions prevent replay.
- Security regression tests run with the standalone Vitest configuration, not the application Vite plugins, so tests can exercise pure security helpers without starting SSR.
- HME Vault links stores via its watch-only pairing QR (src/lib/vault-link/), always gated by the emailed wallet-link code (src/lib/wallet-link-challenge.server.ts); EVM is linked only from an account xpub, never a single address. Its server-only preview helper shows TXC/EVM index 0 for comparison only; sales and monitoring still start at index 1. Why: merchants must verify the same wallet without exposing the reserved main address to payment settlement.
- App emails use a single server-only SES transport, while Cloud auth retains its managed signed handler; this preserves sign-in verification while honoring the app sender choice.
- Customer lists aggregate all paid invoice history through the authenticated caller's RLS-scoped client, grouped by store and normalized email with currency-separated totals; marketing consent is stored separately and written only by validated checkout or paired-terminal operations so receipt capture never implies consent.
- The customer-list route disables SSR because the existing merchant layout hydrates its browser session before displaying children; its authenticated loader must not run without that browser bearer token.
- Wallet-change history reads the existing trigger-backed chain_config_audit through the caller's RLS-scoped client, paginated newest-first; wallet saves refresh it without adding a second audit writer, so every linking path shares one durable record.
- Store pages use /stores/<url_slug>; the $storeId layout resolves slug or legacy UUID into StoreRefContext (useStoreRef) and rewrites UUID URLs to the slug. Why: readable merchant URLs without breaking old links or child-page queries keyed by id.
- Store logos live in a private store-logos bucket and are served via /api/public/store-logo/<storeId>/<file> (raster types only). Why: workspace blocks public buckets; avoids serving SVG/HTML from our origin.
- The public merchant directory is produced only by the SECURITY DEFINER get_public_directory() projection, read with the publishable key (src/lib/directory.server.ts) and exposed at /api/public/v1/directory and /directory. Why: one source of truth for partners; merchant listing choice controls which fields leave the database.
- HME SSO uses the per-site ecosystem key, issuer/site/expiry checks and one-use nonces; permanent member links require a verified local session for first binding, never email-only auto-merging.
- HME popup callers share a flow-scoped BroadcastChannel and validated opener messages; the callback waits for acknowledgement before closing. Why: cross-site popup navigation can remove window.opener without completing the originating sign-in.
- HME referral reporting uses the snippet's last-click cookie and authenticated server-side Hub signup events with delivery tracking; local affiliate history remains first-touch and never grants marketing consent.
- CryptoPOP NFC payments use the dedicated NFC secret for exact-body HMAC requests; approval polling is signed and bound to the originating invoice and terminal, and sent transactions still await NectarPay invoice verification. Why: card broadcasts are not settlement proof and arbitrary payment IDs must not expose other sales.
- The NectarPOS Android app listens for tags with NFC reader mode (MainActivity.enableReaderMode → NectarNfcPlugin.handleTag), never foreground dispatch; Tangem.scan/signHash re-arm it via NectarNfc.rearm() because the Tangem SDK's own reader-mode session disables ours. Why: Senraise firmware stopped re-arming foreground dispatch after the first tag ("tap works once, then deaf"); reader mode delivers every tag continuously.
- Public wallet invoice callbacks and checkout server functions share checkout.server helpers rather than calling RPC wrappers from server routes. Why: server-to-server card callbacks must work in the published Worker without missing function manifests.
- eGiving community splits: only Omni send-to-many TSD credits to stores with egiving_enabled qualify, and every non-merchant output must be an active egiving_recipients address (exactly one program, at least one church, shares summing to the invoice); the merchant slice must reach (100 - EGIVING_DISCOUNT_PCT)% with no tolerance, and the invoice is tagged payment_program/discount_usd before settling. Why: a split must never let ordinary underpayments through.
- The eGiving discount comes from EGIVING_DISCOUNT_PCT in src/lib/egiving.ts, never from stores.egiving_discount_pct; that column is read-only to authenticated (column-level UPDATE/INSERT revoked) and shown disabled in the merchant UI. Why: the eGiving wallet hard-codes its 8% church / 2% program split, so a per-store value would make its fixed payment arrive underpaid.
- Tap-card wallets live in card_partners (admin-managed); the card's NDEF web-address domain picks the partner, else the default, and poll tokens are prefixed with the partner id. Partner keys are write-only via an admin server function (only a fingerprint is readable); the original CryptoPOP row falls back to NFC_PAY_SECRET. Why: multiple wallets join without code changes or exposing keys.
- Admin tables sort through src/lib/table-sort.ts (sortRows/toggleSort) and src/components/admin/sort-header.tsx, never a one-off comparator, so blank cells always sink to the bottom and headings stay keyboard- and screen-reader-labelled. Why: every sortable list must behave the same way.
- Customer signatures are image files in the private sale-signatures bucket (invoices.signature_path); invoices.signature_data_url is only a fallback for a failed upload, and any read must first confirm the caller may see that sale with their own RLS-scoped client before the bytes are returned. Why: the image is rendered in a browser and emailed, so it must never be reachable without a sale-level access check.
- Emails that embed an image go through the raw MIME builder (src/lib/email/mime.ts) as a Content-ID part of a multipart/related message; SES's simple body cannot carry one, and header values are stripped of line breaks so a subject or filename cannot smuggle extra headers.
- Report business days use the selected store's timezone, else the viewer's profile timezone, else the device zone, via src/lib/timezone.ts; sales stay stored in UTC. Why: late-evening sales must land on the merchant's local day.
